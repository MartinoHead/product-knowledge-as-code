# Product Knowledge as Code - Development Guidelines

## Core Principle

This repository implements **Product Knowledge as Code (PKAC)**:

- **Source of Truth:** Product behavior specifications in `knowledge/` directory
- **Derived Artifacts:** Tests are generated from knowledge, not written independently
- **Feedback Loop:** Test failures and production incidents feed back into knowledge updates
- **Version Control:** All knowledge, tests, and code evolve together

## Knowledge-First Workflow

### When Making ANY Code Change

**ALWAYS follow this sequence:**

1. **Update Knowledge Files FIRST** (before writing code or tests)
   - Edit `knowledge/feature-name/feature-name.md` - Human-readable specification
   - Edit `knowledge/feature-name/feature-name.yaml` - Structured rules with acceptance criteria
   - Edit `knowledge/feature-name/feature-name.feature` - Gherkin scenarios
   - Each rule must have a unique ID (e.g., `LISTUSR-001`)

2. **Verify Synchronization**
   ```bash
   npm run verify:sync
   # Must pass: "Knowledge sync OK (X feature(s), md/yaml/gherkin aligned)"
   ```

3. **Generate Tests from Knowledge**
   ```bash
   npm run generate:tests
   # Must generate test scaffolds for API and Playwright tests
   ```

4. **Implement Code**
   - Update endpoint implementation
   - Update service layer
   - Update repository layer

5. **Fill Test Implementations**
   - Complete test TODOs
   - Maintain rule ID references: `test('[RULE-ID] ...', async ...)`
   - Ensure each rule has corresponding test

6. **Verify Everything**
   ```bash
   npm run typecheck
   npm run lint
   npm run test
   npm run verify:sync  # Must still pass
   ```

## Rule for AI Agents

**When implementing features:**

❌ **DO NOT:**
- Write tests independently without knowledge files
- Create test cases that don't reference a rule ID
- Add functionality without updating knowledge files first
- Generate tests without verifying sync
- Accept code changes that break knowledge sync

✅ **DO:**
- Always create/update knowledge files first
- Reference rule IDs in all tests: `[RULEID-001]`
- Run `verify:sync` before committing
- Generate tests from knowledge as source of truth
- Maintain traceability: knowledge → rule ID → test case → implementation

## Knowledge File Structure

Each feature has three synchronized representations:

### 1. Markdown (`feature-name.md`)
- Human-readable feature specification
- Intent, happy path, expected behavior
- Edge cases and non-goals
- API contract examples

**Example:**
```markdown
# List Users

## Intent
Allow authorized clients to retrieve a complete list of all managed users.

## Rules
- LISTUSR-001: List users requires authorization.
- LISTUSR-002: List users returns empty array when no users exist.
```

### 2. YAML (`feature-name.yaml`)
- Structured rules with IDs
- Acceptance criteria for each rule
- Machine-parseable format

**Example:**
```yaml
feature: List Users
rules:
  - id: LISTUSR-001
    title: List users requires authorization.
    acceptance_criteria:
      - Request without auth returns 401
```

### 3. Gherkin (`feature-name.feature`)
- BDD scenarios with rule references
- Given-When-Then format
- Tagged with rule IDs

**Example:**
```gherkin
@LISTUSR-001
Scenario: List users requires authorization.
  Given a request without authorization token
  When list users is submitted
  Then unauthorized response is returned
```

## Test Generation & Traceability

When you run `npm run generate:tests`:

1. **API Test Scaffold** (`tests/api/feature-name.api.spec.ts`)
   - Generated test structure for each rule
   - TODO placeholders for implementation
   - Tags with rule IDs: `[RULEID-001]`

2. **Playwright Test Scaffold** (`tests/playwright/feature-name.spec.ts`)
   - Generated UI test structure
   - TODO placeholders for implementation
   - Tags with rule IDs: `[RULEID-001]`

**Important:** Tests are **generated artifacts**, not hand-written source code. The source of truth is the knowledge files.

## When Tests or Production Incidents Occur

### Test Failure
1. Investigate root cause
2. Update knowledge file if behavior changed
3. Update acceptance criteria
4. Re-run `verify:sync`
5. Re-run `generate:tests`
6. Fix implementation
7. Verify tests pass

### Production Incident
1. Create incident report
2. Update knowledge files with incident-related rules
3. Add new test cases for incident prevention
4. Re-run `verify:sync` and `generate:tests`
5. Deploy fix
6. Mark incident resolved

## Quality Gates (CI/CD)

These gates enforce PKAC principles:

1. ✅ `npm run verify:sync` - Knowledge files must be synchronized
2. ✅ `npm run lint` - Code quality
3. ✅ `npm run typecheck` - Type safety
4. ✅ `npm run test:api` - API tests must pass
5. ✅ `npm run test:ui` - UI tests must pass

**Commit is rejected if:**
- Knowledge sync fails
- Tests don't match knowledge rules
- Missing rule IDs in test names
- Linting or type errors

## FAQ

**Q: Can I write a test without a knowledge file?**  
A: No. Tests are generated from knowledge. Update knowledge first.

**Q: What if the API behavior should be different from knowledge?**  
A: Update the knowledge file, re-generate tests, then update implementation.

**Q: Can I skip test generation and write tests manually?**  
A: No. Manual tests break synchronization. Always generate from knowledge.

**Q: How do I handle emergency hotfixes?**  
A: Still update knowledge files first (even if just a quick note), generate tests, then implement. PKAC is non-negotiable for quality.

**Q: What if knowledge file structure changes?**  
A: Update the sync verification script and ensure all files stay aligned.
